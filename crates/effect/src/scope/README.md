# Ordinary and prepared scope ownership

Ordinary `Scope<E>` retains its existing Clone/Arc API and lifecycle behavior. The additive `PreparedScopePool<E>`, `PreparedScopeOwner<E>` and `PreparedScope<E>` use counted prepared storage and fallible sharing; they call the SAME phase, registration, close/drain, settlement and abandonment engine. This is not a second scope implementation or interpreter. Concrete names/layout choices are implementation mechanisms, not additional user requirements.

## Storage and lifetime

`PreparedScopeLimits` selects a root finalizer capacity and a finite number of simultaneous detached suffix batches. Each batch has that complete capacity; total retained-finalizer allowance is therefore `finalizers * (segments + 1)`, not just the root capacity. `demand::<E>` computes concrete typed collection/control payload and allocation-request counts without invoking business work. Region reports additionally count allocation prefixes, alignment and unsplittable tails.

Preparation provisions all FixedVector batches and the shared Inner/owner metadata in application-selected memory. There is no hidden Arc allocation inside fallible prepared scope/factory preparation. Constructing an ordinary Effect description still allocates its existing operation Arc: into_effect's Result covers pre-held owner sharing, not fallible provisioning of that legacy description domain. This boundary remains explicit outstanding integration rather than a whole-region/fallible-description claim. Event construction contains its existing initially-null atomic pointer; listening/native thread notification and ordinary interpreter continuation/context/output ownership remain outstanding separate domains, not magically accounted by this storage.

The dedicated owner, not a shareable handle, holds canonical asynchronous cleanup authority. `handle`/`try_clone` are fallible and preserve the same backing identity. Owner and close handles are acquired before entering the body. Dropping an unstarted/abandoned owner follows existing synchronous invalidation/owner-loss behavior; it does not invent awaited cleanup acknowledgment. A one-owner `into_effect` handoff coordinates description clones but is consumed once, like existing single-use ownership adapters. The reusable PreparedScopePool provisions finite rows and aggregate batches up front. It checks out fresh generation-bearing scope state for repeated/concurrent descriptions; old observers and detached segment leases prevent row reuse until actual last ownership. Per-scope segment quota is held through settlement, not borrowed from another scope's declared allowance. New-scope admission can close without invalidating admitted cleanup. Both fallible and ordinary body-description factories are supported with explicit capacity mapping before business execution. This is not a completed whole PreparedRun descriptor.

Existing Effect callbacks and registered finalizers require static captures. Prepared scope composition here therefore uses owned static backing; direct borrowed memory/slots/pinned frames retain their real lifetimes elsewhere. No borrowed lifetime is erased or forged into this static boundary, and no product-wide borrowed-storage or Clone exclusion is introduced.

## Transfer and close

A prepared checkpoint acquires an empty physical suffix batch and a retained scope handle BEFORE the nested body/acquisition. Releasing that checkpoint moves the tail into this exact destination, reverses the transfer to preserve registration order, and lets the common drain pop finalizers in reverse order. There is no split_off, new batch allocation or capacity growth in the prepared transfer. The batch and its pre-acquired inner/segment owner remain retained until every finalizer in it settles (or abandonment invalidates its remaining registrations); field order keeps inner state alive through clearing and physical batch return. Invalid/closed checkpoint behavior remains a scope defect; resource-capacity refusal belongs before body entry.

The ordinary System batch retains its existing Vec/split_off behavior. It is not selected as a fallback by prepared suffix transfer. Both owners use the same Open → Closing → Closed transition, join existing concurrent close, keep primary versus cleanup failures distinct and run destructors outside the scope gate. Abandoning a prepared batch clears its registrations before returning it to its pool.

Registered operations and abandonment callbacks use the common system/reserved one-shot owner representation. A prepared factory installs its one-shot callback in checked physical frame storage. Consuming the callback payload does not return its physical reservation: a stack-only input-builder transfers the empty frame into the existing terminal continuation, retaining it through asynchronous completion or abandonment. The retained wrapper drops callback captures before releasing the frame; the common paths introduce no extra continuation allocation. Finalizer batch/inner/segment ownership remains retained across the same await. Resource acquisition additionally needs a pre-held acquisition/abandonment bundle and prepared resource-value ownership; that integration is not replaced by a pure cleanup factory.

Capacity-refused or closed registration awaits the rejected finalizer immediately, preserving the mapped capacity failure or closed-scope defect as primary and appending cleanup failures. Mapper/factory panics retain their defect channel. Refusal/close/wait/aggregation still use existing ordinary interpreter/listener/control routes in this partial integration; they are not claimed allocation-free or whole-process strict. No expected capacity failure is silently converted into Die for an infallible Effect.

## Typed plans and macros

`PreparedReleasePlan` is an inert typed factory descriptor. Its callback layout is compiler-derived before invocation; its factory storage demand and frame provisioning helpers do not execute cleanup. `PreparedRelease` stores factory captures/sharing in the selected counted memory. No Clone requirement is imposed on payloads or the factory.

Existing macros now expose scope preparation/owner handoff, pre-held checkpoint/release and close, plus finalizer planning/preparation/registration. Their field argument boundaries retain concrete callback types and single source-order evaluation. Owning mode selection is explicit: scope prepare returns a fallible owner, prepared handoff returns a fallible Effect description, and finalizer registration maps capacity through the supplied error mapper. Ordinary modes are unchanged. Native DSL registry edges are exact owner/method associations, not broad lint allowances.

Actual resource acquisition now has a separate PreparedResourcePlan/Binding/Value companion. Preparation counts the acquisition/release/mapper recipe and resource cells. Before acquisition, the binding promises a physical root entry, resource cell, all shared/close handles and distinct callback/abandonment frames. Other registrations cannot steal promised entries. Raw success installs guarded ownership before cancellation/publication, then commits the entry or awaits protected refusal cleanup. Native acquisition errors retain their existing channels; preclosed scope admission reports the existing registration defect without entering acquisition. Capacity has its explicit mapper, not a capacity-to-Die cast. Abandonment invalidates synchronously before closed notification. The callback frame is repurposed from its typed enclosing operation+owner payload to retain the resource owner through release completion/drop. Closed observers retain cell identity and reduce capacity rather than observing a reused generation.

The owned prepared Exit-future release leaf reserves pending/completion storage before invoking its FnOnce factory, supports non-Clone owned captures and never falls back to a system future. The standalone leaf reserves at cleanup dispatch and is not itself a resource preflight contract. Concrete future resources instead use PreparedFutureResourcePlan/Binding: typed demand includes pending, completion and T-bearing native-start layouts; preflight reserves all three protected cleanup cells before acquisition, alongside callback/abandonment/entry/resource/mapper/close ownership. Cleanup starts from already owned reservations, with no new capacity claim. Partial vectors roll back before acquisition. Native-context entry/restore uses the same protocol and evaluator with System/Reserved storage adapters. The concrete path also pre-holds entry tag, restore continuation, invocation and restore tag cells: seven cleanup cells total. Demand includes their actual Context/Exit/callback captures and both tag layouts; accepted cleanup makes no system More/tag/restore allocation or late capacity claim for these wrappers. Ordinary callers retain their System lane. Shared context/origin/trace/cancellation pointees, caller continuation and root/transitive metadata are not falsely charged by counting a pointer; those remain explicit integration work. Opaque Release-returning recipes report cleanup=None rather than being falsely treated as complete typed future demand. Arbitrary transitive callbacks and complete generated run/context/provider admission remain unfinished.

The cafe receipt application uses this actual prepared resource binding and a reusable scope pool, writes through the checked receipt handle and retains its real non-Clone TextLease until native stdout flush returns in concrete pre-admitted prepared cleanup. Its cleanup pool count/layout come from the actual compiler-derived start/future/completion demand, not a guessed cleanup-frame size. It is source-checked/linted, never executed in this phase. It has only been checked/linted, not executed. Complete generated run descriptors and multi-domain cleanup working-set admission, lexical resource-use/Layer/integration migration, bounded waiters/context pointees/root output/error accumulation, borrowed-run/provider/transport coupling and all later runtime validation remain required. Owner loss does not fabricate asynchronous native completion: provider job/operation ownership must still retain its own reservations until actual settlement. Tests/builds/runtime measurements remain deferred until the user's full 13-crate implementation milestone.
