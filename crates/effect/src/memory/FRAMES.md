# Prepared frames beneath the existing interpreter

This is an additive W05 production seam, not complete prepared execution or a replacement interpreter. Runtime validation remains deferred until the full 13-crate implementation is in place.

`PreparedMemory::frames` provisions fixed, aligned frame payloads plus their typed-slot control and intrusive destruction records at startup. `FramePool::reserve<T>` checks the actual concrete layout and checks out a physical cell, using nonblocking metadata admission. A failed multi-frame reservation returns prior empty cells before user factory invocation. `FrameReservation::initialize` creates a `PinnedValue<T>` at its final address; the underlying mutable slot is private. Projection exposes only `Pin<&T>` or `Pin<&mut T>`. Extraction requires Unpin. Destruction marks the cell uninitialized, drops T in place and only then returns its capacity. A public mutable SlotLease is not treated as a pinned future.

Borrowed frame storage retains its real Rust lifetime for direct use. Runtime callback erasure separately requires owned static backing and Send/static captures, matching the existing Effect callback contract; no lifetime transmute is used. Forgotten frame ownership can reduce capacity but cannot authorize reuse of live storage.

`RunFrames` holds distinct pre-provisioned work and cleanup pools; aliases of the same pool are rejected rather than pretending to provide independent cleanup headroom. `Effect::run_with_frames` and `run_cancellable_with_frames` supply these pools through the existing Context/FailureOrigin ownership path. Child/parallel contexts retain that selection. Protected contexts select cleanup frames without borrowing work capacity. Existing failure-origin/clock-frontier semantics remain separate from frame selection.

The existing `Step`, `Finish` and evaluator now use system-or-reserved one-shot/pending owners. Ordinary operations select their existing system lane; the ordinary source changes from Step constructors to lowercase system helper methods are mechanical wrapping, not domain migrations. The supplied frame owner polls pinned payloads and uses the same Suspended versus Composed handling, clock acknowledgment, publication, native context and cooperative yield loop.

The `effect_future!` prepared mode requires an explicit `on_capacity` mapper. It reserves both a named panic-catching future wrapper and its completion transition before invoking the future factory. Missing storage, capacity or layout errors become the explicitly mapped E outcome; there is no system fallback or hidden Die for memory refusal. The mapped refusal still uses ordinary continuation routing and can allocate system metadata; it is not yet a fully prepared rejection/control path. Future/factory panics retain their existing defect channel. Completion uses its already-owned transition cell, not a new fallible allocation after the business result exists. This is one real leaf adapter; it is not the final effect_prepare descriptor/macro or a bound for arbitrary dynamic callbacks.

Prepared static runtime frames use an intrusive lane of the existing global per-thread destruction registry. Each queued cell stores its own lease and next/root record in pre-reserved metadata. A draining root retains itself while descendants are queued, so neither roots nor pending nodes refer to reused cells. Registry bookkeeping is mutex-protected; payload destructors and owner release run outside the lock. Reentrant drops enqueue rather than recursively descending. Release/drain guards return storage during a single destructor unwind; a second panic during unwind retains ordinary Rust double-panic behavior. No prepared node creates a HashMap, Vec or Box. The legacy FlatDrop system lane remains for ordinary owners.

Registered scope callbacks transfer their physical frame into the existing terminal continuation rather than returning it when the payload is consumed. Prepared resource callbacks initially contain `Settlement<Operation, Owner>`; after moving the never-pinned payload out, the private shim installs Owner in the same frame until cleanup completion/abandonment. Owner is a field of the original unpacked enclosing Rust type, proving size/alignment fit; initialization/destructor metadata changes to that exact new type, with no live pin/projection crossing the move. The enclosing type is not a public arbitrary layout-erasure escape. Resource cell quota consequently survives the async cleanup await. A scoped loss guard also settles Failed on capture-destructor unwind instead of leaving Closing forever. Native-provider owner loss still requires its own actual-settlement ownership; Drop is not asynchronous acknowledgment.

The owned prepared Exit-future Release companion supports FnOnce captures and uses the same two-frame leaf adapter under protected cleanup. Its standalone reservations occur at cleanup dispatch. The concrete PreparedFutureResourcePlan/Binding now reserves exact pending/completion and T-bearing start-transition cells BEFORE native resource acquisition and retains them until start/completion/destruction. The leaf and resource path share the same reserve/start and pinned poll adapter. Typed cleanup demand reports all three layouts and finite counts; startup selects that exact union layout for the independent cleanup pool. Opaque Release recipes expose absent concrete future demand rather than silently falling back. Full generated transitive/control/context/provider admission remains required; concrete cleanup Contextual/restore wrappers now have four additional pre-held cells (entry tag, restore continuation, invocation, restore tag), totaling seven with start/pending/completion. System/Reserved TaggedStep ownership feeds the SAME iterative evaluator, preserving context selection/restoration and poll guards. The capture layouts are reflected by PreparedContextualDemand and included in startup cleanup sizing. Ordinary tag/restore paths, shared context/origin/trace/cancellation pointees, caller continuation and root/transitive output/control storage remain explicit integration obligations, not claimed covered by these inline layouts.

Accounting includes frame payload allocations, typed-cell/destruction metadata and allocator headers/padding through the existing region reports. The fixed process-global registry, native synchronization/thread metadata, description owners, existing output/context Arcs, Contextual Box tags, ordinary dynamic scope state/Registered finalizers and ordinary callback owners are not magically covered by these frames. Explicit prepared scope/resource state and callbacks now have separate counted pools, without implying coverage of the ordinary lanes. Their integration remains required, along with generated complete demand/layout descriptors, reserved interpreter context/output/finalizer/child storage, destruction coverage for recipe owners and physical admission coupling. No zero-allocation/full-region/whole-process claim follows from the current leaf adapter.

The bounded cafe receipt application now selects real work/cleanup frame pools and its prepared future mode while retaining explicit payload/output ownership. It is source checked/linted only, not executed or used as an executable verification probe. Full application examples and native/provider/web integration remain required by the complete plan.

A prepared latch uses `PreparedLatch::prepare` with a caller-selected listener capacity. `wait()` reserves one listener and returns an owned `PreparedLatchWait`; the raw future only waits for opening. An admitted wait can be moved into the existing prepared `effect_future! { exit_with_context; body: move |_environment, context| wait.with_context(context), }` graph form. The context adapter uses the graph's prepared cancellation listener and returns the existing `Exit` channels. Each `wait()` is one pre-admitted invocation, not a reusable recipe or automatic per-run graph reservation. `PreparedLatch::storage_bytes` reports the latch, notification and listener-pool layouts, excluding partition allocator headers and padding.

`prepared_oneshot` prepares a single-use channel and one actual listener before either endpoint escapes. Sending consumes its unique sender and returns the original value if the receiver is gone; the receiver drains a delivered value before reporting sender closure. Dropping a receiver destroys any undelivered value outside the channel lock. `PreparedOneshotPool` preprovisions a caller-selected number of channel controls, each with its own listener pool, and recycles a channel only after both endpoint owners retire. Its storage report includes their pool layouts; allocator headers and padding remain separately charged.

`prepared_watch` separately provisions its receiver-listener and retained-version capacities. Publishing reserves a fresh version before replacing the current one and returns the original value on refusal; at least two version slots are needed to publish while a current version exists. Views retain their exact generation-bearing version and borrow its payload without cloning it, so held views consume version capacity. The receiver marks the latest generation seen only after successfully retaining a view, or when `changed` reports an unseen update; an unseen final update precedes sender-close notification. `publish_retained` publishes even without receivers. These APIs do not yet replace host watch usage or implement `send_replace` / `send_if_modified` compatibility. Pool layout reports exclude allocator headers and padding.

`PreparedDeferred` reserves its actual outcome cell and a caller-selected listener pool. `publish_now` returns a duplicate candidate intact; a shared view retains that cell, and `try_take_owned` refuses while an external shared view remains. The admitted wait is a notification future; `with_context` uses the graph's prepared cancellation listener. The prepared view offers an immutable borrow guard without cloning A or E. Ordinary `SharedExit::with` catches panics and constructs a diagnostic through the separate W05-18 path; the guard does not claim that panic-catching behavior.

`PreparedCancellation` reuses the prepared runtime context domain for explicitly bounded nodes and cancellation listeners. Child nodes retain their real parent links; admitted waits unlink their listener before releasing the node. Zero clock ticks are configured and no clock capability is exposed. Its storage report includes the domain pool and node/listener/release-vector payloads; per-allocation headers, alignment padding and allocator bookkeeping remain separately charged.

`PreparedSemaphore` uses a caller-selected physical waiter/listener capacity and preserves weighted FIFO ordering, issued/available capacity checks, close and permit accounting. `acquire` admits a concrete owner and, when necessary, a queue entry and listener before returning the wait future; it may reserve immediately available permits before the future is polled. Dropping an unpolled or pending acquisition returns any grant or unlinks its queue entry, and an acquired permit retains its owner through release. `with_context` uses prepared graph cancellation. `storage_bytes` includes the state, FIFO-entry payload and notification pools; region allocator headers and padding are charged separately. Partitioned semaphore and other synchronization owners still require their own prepared integration.

`PreparedPartitionedSemaphore` currently prepares a fixed sorted key index, all per-partition semaphores and an equally sized retirement batch. Its lookup returns the original key on refusal, and keys remain indexed in `Ord` order. Snapshot prune/close and their cleanup-panic handling are not implemented; the companion must not be treated as full partitioned-semaphore parity. Layout reporting excludes separate allocator headers and padding.

Prepared panic diagnostics require an explicit `PreparedPanicConfig` specifying slot count, bytes per string message and either summary or UTF-8-prefix overflow. Region text and registry payload are reported separately from startup System Arc control count and its pinned-toolchain requested-layout estimate; allocator overhead and the runtime-provided panic Box remain separate. Graph and concrete-future plans can receive a pool through `panic_diagnostics`; each caught operation reserves its own slot before its callback. An unconfigured path uses the ordinary panic conversion and is not a strict diagnostic guarantee. Admitted scope/finalizer/resource/close variants return initial diagnostic refusal before the one-shot Effect or mapper runs; ordinary `try_scoped`, `register`, `acquire_scoped`, `close`, and ordinary prepared-frame adapters retain their legacy refusal handling. These diagnostic mechanisms do not establish bounded allocation for arbitrary user code.
